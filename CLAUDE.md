This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm install
npm run dev:all      # API (4000) + Vite (3000) together — the normal dev command
npm run server       # API only
npm run dev          # Vite only, port 3000, host 0.0.0.0, proxies /api -> 4000
npm run lint         # tsc --noEmit — the only check in the repo
npm run build        # vite build
npm start            # Express serves dist/ + /api on port 4000
```

There is no test framework, no ESLint, and no CI. `npm run lint` (type-check) is the full verification story.

`DISABLE_HMR=true` disables both HMR and file watching in [vite.config.ts](vite.config.ts) — set by AI Studio to prevent flicker during agent edits. Leave that block alone.

## What this is

A canteen meal-tracking system for a Korean-Vietnamese manufacturing site, running on **real data** from a BioStar card-reader installation. React 19 SPA + Express API + SQL Server. UI text is Vietnamese; keep it that way.

`@google/genai` sits in [package.json](package.json) but no source file imports it and nothing reads a Gemini key — this stopped being a Google AI Studio applet when it was wired to SQL Server.

## Architecture

**Three tiers.** `src/` (React) → `server/` (Express, plain ESM JavaScript) → SQL Server stored procedures. The server is a thin wrapper: every endpoint in [server/routes.js](server/routes.js) binds validated params and calls exactly one `SA_*` procedure. **No SQL is written in JavaScript** — if a query needs to change, it changes in [db/03_procedures.sql](db/03_procedures.sql) and gets redeployed.

**Two databases on one instance.** `BioStar` holds the source data (`TB_EVENT_LOG`, `TB_READER`, `TB_USER`, `TB_USER_DEPT`) and is **read-only — never write to it**. `QLSA` holds this system's `SA_*` config tables and all procedures, which read cross-database into BioStar. Connection string points at `QLSA`. The one QLSA table that is not `SA_*` is `TB_EVENT_LOG_DEL`, which mirrors the BioStar table it is named after — see the deletion section below.

**SQL scripts are the schema source of truth.** [db/01_schema.sql](db/01_schema.sql) (16 tables), [db/02_seed.sql](db/02_seed.sql) (catalog data), [db/03_procedures.sql](db/03_procedures.sql) (all procedures). All three are idempotent and must stay runnable in order on a fresh QLSA. Deploy with `sqlcmd -f 65001 -I` — `-I` for `QUOTED_IDENTIFIER` (required by the PERSISTED computed columns), `-f 65001` to read the UTF-8 files without mangling Vietnamese.

**Target server is SQL Server 2012 Express.** No `CREATE OR ALTER`, no `DROP ... IF EXISTS`, no `STRING_AGG`. `03_procedures.sql` drops every `SA_*` proc in a header batch, then plain-`CREATE`s them.

**Single owner of all state.** [src/App.tsx](src/App.tsx) fetches everything and passes both data and async mutation callbacks down as props. There is no context, reducer, or store. Views never call the API directly — they receive `onSave` / `onDelete` and surface errors via `alert`. Adding a data domain means: table + procs in `db/`, route in `server/routes.js`, client fn in [src/services/api.ts](src/services/api.ts), `useState` + handler in `App.tsx`.

**Tab-based routing without a router.** `TabType` in [src/components/Navbar.tsx](src/components/Navbar.tsx) is the union of tab ids; `App.tsx` renders one view per `activeTab === '...'` branch. A new screen = new `TabType` member + `navItems` entry + branch in `App.tsx`.

**Views are self-contained.** Each `src/components/*View.tsx` receives raw `logs` plus the date range, does its own `useMemo` filtering by `l.actualDate >= startDate && l.actualDate <= endDate`, and computes its own aggregates inline. Repeating an aggregation across views is the existing convention; only genuinely shared logic lives in [src/services/mealEngine.ts](src/services/mealEngine.ts) (pure functions, no React).

**Two totals in the cost-report tab are deliberately different, and `reconcileCost` is what ties them together.** The TOTAL of "Thống kê suất ăn tháng" is the invoice figure — meals *plus* milk. The TỔNG CỘNG PHÂN BỔ of "Phân bổ theo BP" is meals only, because milk is entered per day with no beneficiary department to charge. The gap between them is always exactly milk plus extra costs. `reconcileCost` in [reportModel.ts](src/components/financial/reportModel.ts) is the single source of those figures (`mealAmount` / `milkAmount` / `extraAmount` / `grandTotal`) behind the tab's summary cards and the reconciliation rows at the foot of the department table, on screen, in CSV and in Excel. If you add a cost line that is not attributable to a department, it belongs in that reconciliation, not in `buildDeptAllocation`.

**"Điều Chỉnh Số Liệu" deletes punches for real, and the deleted rows are archived in a `_DEL` table.** The popup ([CostAdjustmentDialog.tsx](src/components/financial/CostAdjustmentDialog.tsx)) lets the user drop the punch-loss meals and any number of ad-hoc `(staffType, date, shift, quantity)` amounts before settling with the canteen. `applyCostAdjustment` in [reportModel.ts](src/components/financial/reportModel.ts) only *computes* which punches those are; the popup then sends their ids to `SA_MealLogDeleted_Save` and the change is **database-wide** — Dashboard, Lịch Sử Chấm Ăn, every cost report and the 12-month trend all stop counting them, so no screen has to remember to subtract anything. **The one exception: a deleted *loss* punch is still shown in Suất Ăn Mất Mát, unchanged.** The popup sends losses as `lossIds` and ad-hoc picks as `ids`; they land in `TB_EVENT_LOG_DEL` with `DeleteKind` `'MAT_MAT'` / `'BAT_KY'` (pre-existing rows are `'BAT_KY'`). `SA_MealLog_GetByRange` still returns `'MAT_MAT'` rows with `lossDeleted = 1`; [App.tsx](src/App.tsx) gives every tab `activeLogs` (those rows dropped) except Suất Ăn Mất Mát and Báo Cáo Chi Phí, which get the full `logs` — the loss tab to display them, and `FinancialReportView` to drop them from `classified` itself while still evaluating losses on the full set, so a punch's Bị trừ / Không trừ class never shifts because a neighbour was deleted. `abnormalList` (Navbar badge, Dashboard loss card) is computed on the full set too, so those agree with the loss tab. **Ad-hoc deletions never touch a loss case**: `applyCostAdjustment` skips every punch of a (working day × user) that has any loss — whether or not losses are being deducted in that run, and including already loss-deleted ones — because an ad-hoc delete is `'BAT_KY'` and would vanish from the loss tab, and removing even the *valid* punch of such a day would un-make its duplicate. Skipping whole cases is sufficient: losses are evaluated per case, and removing punches from a clean case cannot create one. The loss part has three scopes (`LossDeductScope`): all losses, `CHARGEABLE` (only `BI_TRU`) and `FREE` (only `KHONG_TRU`, the <10-minute re-swipes) — `inLossScope` is the one predicate both the preview and the apply path use. Ad-hoc deductions match on `reportDate` (the day column the user is looking at), consume punches latest-first so repeated runs are identical, never double-delete a punch already taken as a loss, and report a `shortfall` rather than going negative when the day/shift has fewer punches than requested. **The "Upload Excel" button in that section is a faster way to type, not a second code path**: each valid sheet row becomes one ordinary `AdHocDeduction` appended to the same draft, so it is priced by the same `applyCostAdjustment` and written by the same "Xóa Khỏi Dữ Liệu" button — the file cannot skip the confirmation step, and importing can never produce a different number than typing the same rows by hand. Rows are validated before the preview and a rejected row names the column and the reason; a date outside the filter range is a *warning* (it deletes nothing) rather than an error, because the hand-typed form allows it too.

**Nothing is actually deleted from BioStar — deletion is an exclusion list that doubles as the archive.** `BioStar.dbo.TB_EVENT_LOG` is read-only, so a "deleted" punch is one whose row is copied into `QLSA.dbo.TB_EVENT_LOG_DEL`, and both procedures that read punches — `SA_MealLog_GetByRange` and `SA_MealCost_GetMonthly` — carry a filter against it (`SA_MealLog_GetByRange` lets `DeleteKind = 'MAT_MAT'` rows through flagged `lossDeleted`, for the loss tab only; the client drops them everywhere else). **Change one and you must change the other**, or the monthly statement and the 12-month trend disagree. That table's first nine columns are a byte-for-byte mirror of `TB_EVENT_LOG` (the requirement that a `_DEL` table look exactly like the table it shadows), with `DeleteBatchId` / `DeletedAt` / `DeletedBy` / `DeleteReason` appended *at the end* so a restore into BioStar is one `INSERT … SELECT` over the first nine columns — the statement is written out in the table's comment in [db/01_schema.sql](db/01_schema.sql). In practice the BioStar row never left, so `SA_MealLogDeleted_Restore` just deletes the archive row. Every "Áp dụng" is one `DeleteBatchId`, and the popup lists batches (`SA_MealLogDeleted_Get`) with a per-batch restore, so a bad settlement is undone whole. Ids travel down as a table-valued parameter (`dbo.SA_EventIdList`, created in `01_schema.sql` because `03_procedures.sql` drops and recreates everything it owns and a type in use cannot be dropped); `callProc` in [server/db.js](server/db.js) binds a TVP when the param's type is `null`.

**The one exception is the cost-report tab.** `FinancialReportView` hosts eleven sub-reports picked from a button menu; they live in [src/components/financial/](src/components/financial/) and all read one shared classification pass ([reportModel.ts](src/components/financial/reportModel.ts) `classifyLogs`) so the monthly statement, the allocation tables and the six per-shift sheets can never disagree about the same punch. Add a report = new component there + entry in `SUMMARY_MENU` + branch in `FinancialReportView`.

**Every cost-report table is built in `reportModel.ts`, never in its component.** `buildMonthlyStatRows`, `buildAllocationColumns`, `buildDeptAllocation`, `buildShiftPivot` and `YEARLY_SERIES` are the single source for both the on-screen table and the corresponding sheet of the "Báo cáo tổng hợp" workbook ([workbookExport.ts](src/components/financial/workbookExport.ts), lazy-loads `exceljs`, one sheet per menu entry). A component may only map a row's semantic `tone` to Tailwind classes; `workbookExport` maps the same tone to ARGB fills from [workbookTheme.ts](src/components/financial/workbookTheme.ts).

**The workbook ships live Excel formulas, so source cells hold values and derived cells hold formulas.** Row totals, amounts (`= count × unit price`), group subtotals, day totals and grand totals are all `{ formula, result }` cells built from the `colLetter`/`addr`/`rowRange`/`colRange`/`sumOf` helpers — the user edits a count or a price in the file and everything downstream recomputes. Three things this constrains: **never round a number that a formula multiplies** (the allocation sheet's average unit prices must be written in full or `qty × price` drifts off the true amount and the sheets stop reconciling — the display stays rounded via `numFmt`), the department sheet's price row holds a real number formatted `#,##0,"K"` rather than the string `"65K"` so `SUMPRODUCT` can reach it, and a merged day cell keeps its value only in the top-left so `SUM` over the row counts it once. Every formula also carries `result` for viewers that don't calculate, and `wb.calcProperties.fullCalcOnLoad` makes Excel recompute on open. Change a table's colours on screen and you must change the matching entry in `workbookTheme.ts`, or the Excel file stops looking like the web page.

**Excel *import* is shared; Excel *export* is not.** There are two exporters — [workbookExport.ts](src/components/financial/workbookExport.ts) for the multi-sheet "Báo cáo tổng hợp" and [lossStatsWorkbook.ts](src/components/lossStatsWorkbook.ts) for the one pivot in Suất Ăn Mất Mát — and each owns its own cell-drawing helpers on purpose, because what decides a sheet's layout is the web table it mirrors, not a shared frame. The one thing they *do* share is [workbookTheme.ts](src/components/financial/workbookTheme.ts): change a table's colours on screen and you change them there, and both files follow. Both lazy-load `exceljs` (~950KB) so it stays out of the main bundle, and both set `fullCalcOnLoad`. [src/services/excelImport.ts](src/services/excelImport.ts) holds the mechanical half of "Nhập từ Excel" — lazy-loading `xlsx`, matching column headers against an alias table, normalising date and number cells. Views keep their own validation because what makes a row valid is per-tab. Three screens use it: Quản Lý Sữa, Nhập Thủ Công Ca and the "Xóa suất ăn bất kỳ" section of the Điều Chỉnh Số Liệu popup, each pairing it with a "Tải file mẫu" button whose sample sheet must keep using the first alias of every column. **`normalizeDate` returns a date only if it is a real calendar day** — `isoIfReal` rebuilds it through `Date.UTC` and compares the parts back, because `2026-15-09` (a file written US-style) and `2026-02-31` match every regex and then die in SQL Server as `Error converting data type varchar to date`, a 500 that names neither the row nor the column. Day-first is deliberate: a `dd/mm/yyyy` cell is never re-read as `mm/dd/yyyy`, since guessing a wrong date is worse than rejecting the row. `parseDate` in [server/routes.js](server/routes.js) carries the same check, so the API answers 400 in Vietnamese rather than letting SQL Server answer in English. **Import failures are reported per row, not per file**: `onImport` saves every row it can and returns `{ index, message }[]` instead of throwing at the first bad one, and the preview modal writes each message into that row's Trạng Thái cell and marks the saved ones so a second click cannot insert them twice.

**Aggregation is client-side by design.** `SA_MealLog_GetByRange` returns raw punches (~50K rows / 1.2 MB gzipped for a month) and the browser aggregates. `compression` middleware is what makes this viable — don't remove it.

## Domain rules that drive the code

These rules are implemented **twice** — in `SA_MealLog_GetByRange` (authoritative, applied at read time) and in `mealEngine.ts` (`determineShift`, `getActualWorkDate`, now unreferenced but kept as the documented spec). Change both together.

- **A punch deleted through "Điều Chỉnh Số Liệu" is gone from every count.** `SA_MealCost_GetMonthly` (and the guest punch counts) exclude anything listed in `QLSA.dbo.TB_EVENT_LOG_DEL`; `SA_MealLog_GetByRange` excludes everything except `DeleteKind = 'MAT_MAT'`, which it returns flagged `lossDeleted` so only Suất Ăn Mất Mát shows it — see the deletion section under Architecture. Any new procedure that reads punches must exclude the same rows.
- **`actualDate` is the plain calendar date of the punch** — `CAST(LogTime AS date)`. There is no workday shift: a punch at `2026-08-11 00:48:37` belongs to `2026-08-11`, not the previous day. (An earlier 08:00→08:00 workday rule that subtracted 6601 seconds was removed; if you find that constant anywhere, it is stale.) `actualDate` is the SQL-side key (overrides, monthly grouping); on screen, every per-day row and "Ngày làm việc" column shows the **working day** (`getCostReportDate`, see the working-day bullet below) — Lịch Sử Chấm Ăn's pivot, Hàn Quốc vs Việt Nam's day rows, the drill-down popups. `logDateTime` drives range filtering, display, and ordering.
- **`mealDate` ("ngày của ca") is a second, narrower date key, used for birthday matching only** — `actualDate`, except that the after-midnight half of a wrapping shift (CA1 00:00–01:50) belongs to the *previous* calendar day, because CA1 22:50→01:50 is one shift of the day it starts. It exists in exactly two places: `getMealShiftDate` in [src/services/mealEngine.ts](src/services/mealEngine.ts) and the `md` CROSS APPLY of `SA_MealCost_GetMonthly` — change both together. It does **not** replace `actualDate` anywhere else, and it is **not** the day-column key of the cost reports — see `reportDate` below.
- **`reportDate` is the day-column key of the cost reports, and only of those** — `actualDate`, except that the before-midnight half of the wrapping shift (CA1 22:50–23:59) belongs to the *next* calendar day, because the canteen books the whole night shift against the day it ends. Filtering 18 22:50 → 19 12:00 therefore produces columns for the 19th only; extend the range to the end of the 19th and the 19th's 22:50-onwards punches add a column for the 20th. It lives in `getCostReportDate` ([src/services/mealEngine.ts](src/services/mealEngine.ts)) and is read in exactly one place — `classifyLogs` in [src/components/financial/reportModel.ts](src/components/financial/reportModel.ts), which puts it on `ClassifiedLog.reportDate`; every table and Excel sheet under `financial/` groups by that field. It is deliberately the mirror image of `mealDate` and must not be substituted for it: birthday pricing still keys on the day the shift *starts*. `SA_MealCost_GetMonthly` aggregates by month and is not affected.
- **The global range filter is second-precision, and a day is a working day: (D-1) 22:50 → D 22:50, in every menu.** `startDateTime` / `endDateTime` are `"YYYY-MM-DD HH:mm:ss"` and both bounds are inclusive. Views filter logs on `l.logDateTime`, not `l.actualDate`. 22:50 is the wrapping shift's start (`workDayStartTime`), so filtering from 25 22:50 begins with CA1 of the 26th — for punches, manual entries and supplies alike. The default range and the Hôm nay / Tháng này / Tháng trước buttons cover whole working days via `workDayFilterRange` ((from-1) 22:50:00 → to 22:49:59, the last second dropped so consecutive ranges never share a punch), and "Hôm nay" after 22:50 is already tomorrow (`workDayOf`). **`startDate` / `endDate` in `App.tsx` are the working-day range the filter touches (`costWorkDayRange`), not the date part of the bounds** — that is what date-only screens (Quản Lý Sữa, labels, file names) receive. The one exception is `fetchMealLogDeletions`, whose procedure filters by calendar date, so its callers pass `startDateTime.slice(0, 10)` / `endDateTime.slice(0, 10)`. Manual entries and supplies are placed on the time axis and filtered there (see their bullets), on every screen.
- **Six shifts, time-window based**, stored in `SA_Shift` and resolved by an `OUTER APPLY ... TOP 1 ORDER BY SortOrder`. CA1 night (22:50–01:50) has `WrapsMidnight = 1`, which switches the predicate from `AND` to `OR`. CA2 04:30–06:30, CA3 06:45–08:10, CA4 10:40–13:30, CA5 16:30–18:40, CA6 18:45–20:10, else `'Khác'`.
- **Three BioStar readers**, in `SA_Reader`, keyed by `nReaderIdn`. `TA-102` (`547244627`) is the Korean canteen — `IsKoreanMachine` sets `MealLog.isKorean`, which is **display only**. It must never reach a pricing path: a visitor or an SP-department employee punching at TA-102 is still priced as Vietnamese.
- **`nDateTime` is epoch seconds in LOCAL time** — `DATEADD(SECOND, nDateTime, '1970-01-01')` gives the wall-clock punch time with no timezone adjustment. Date-range params are converted to an epoch range so the query seeks the clustered PK `(nDateTime, ...)` instead of scanning 3.3M rows. Don't filter on a converted datetime.
- **Valid punch events** are the `nEventIdn` values in `SA_MealEventCode` (39, 43–53, 55, 58, 59, 61, 62) — inherited from the legacy `PKG_TKSA001@GET_LIST` proc. Other event ids are device noise (door open, tamper) and must be excluded.
- **`TB_EVENT_LOG.nUserID` (int) joins `TB_USER.sUserID` (varchar).** The procedure resolves this via `TRY_CAST(sUserID AS int)` into a `#Users` temp table, deduped with `ROW_NUMBER()`.
- **Two-level department hierarchy.** `SA_DepartmentMapping` folds ~41 small departments into large ones (`CSP`, `LFEM`, `SMT`, `SP`, `QC`, `WLP1`, `WLP2`, `R&D`, `KR`, `Khác`); unmatched falls through to `'Khác'`. Users edit mappings live in the Ánh Xạ Bộ Phận tab.
- **Conditional mapping via `SA_DepartmentMappingRule`**, which *overrides* the default mapping. The live rule: `Khach cong tac` whose `sUserName` contains `Business` → `KR`; everyone else in that department → `SP`.
- **A single view resolves "which large department is this person in", and everything reads it.** `SA_UserDeptResolved` ([db/03_procedures.sql](db/03_procedures.sql)) dedupes `TB_USER` and applies the full precedence **per-person override > rule > mapping > `'Khác'`**. `SA_MealLog_GetByRange` and `SA_MealCost_GetMonthly` each just pour it into their `#Users` temp table, so the heavy join still happens once and the four callers cannot drift apart. The view is dropped and recreated by `03_procedures.sql` alongside the procedures (the drop header covers `sys.views` named `SA_*` too) — put any new resolution rule *in the view*, never in a caller.
- **Individual business guests can be re-pointed at any large department, and that is the only per-person override there is.** Guest cards are shared, and each visitor works with a different department, so `SA_GuestDeptOverride` (`sUserID` → `LargeDeptCode`) lets the user send one guest's meals to SP, LFEM, … while the rest of the group stays wherever the rule put them. **It only applies to people a conditional rule swept up** (`SA_UserDeptResolved.IsRuleMatched = 1` — today exactly the `Business` guests); `SA_GuestDeptOverride_Save` re-checks that and raises rather than trusting the client, so the API cannot be used to move a regular employee. The scope is expressed as "rule-matched", not as the literal string `'Business'`, because the rule is user-editable data and copying it into a second place is how the two get out of step. Pricing needs no extra wiring: `StaffType` is `'KR'` iff the large department is `KR`, so a guest moved to SP is priced as Vietnamese everywhere, birthday meals included. Edited in the Ánh Xạ Bộ Phận popup, below the mapping table.
- **An override is one dated period, a guest has many of them, and that is why the view can no longer decide a punch's department by itself.** A guest card is handed on to the next visitor, so a row of `SA_GuestDeptOverride` is a *period*: `(UserId, EffectiveFrom, EffectiveTo)` → `LargeDeptCode`, keyed by an `OverrideId` identity, either date `NULL` = unbounded and both `NULL` = forever (what the rows predating the columns mean). One guest can hold 01–10/08 → SP, 11–20/08 → LFEM, 01–15/09 → QC as three independent rows; **two periods of the same guest may not overlap**, which no CHECK can express (it looks at other rows) so `SA_GuestDeptOverride_Save` enforces it and raises naming the clashing period. Adjacent is not overlapping, so a period slots into the gap between two existing ones, and a period may start in the past — last month's figures simply recompute. The date compared is the punch's **`actualDate`** — not today, and not `reportDate`: which department a person belongs to is a property of them at the moment they punched, not of the day column the meal is invoiced under. A filter spanning several periods therefore splits itself, with no screen slicing date ranges by hand. `SA_UserDeptResolved` returns only the *inputs*: `BaseLargeDept` (rule > mapping > `'Khác'`, what a punch outside every period gets), `IsRuleMatched`, and `LargeDept` = **effective today, display only**. Both punch-reading procedures pour the periods of rule-matched users into a `#Ov` temp table and pick one per punch with `OUTER APPLY ... TOP 1` — **`#Ov` and that APPLY are copies in `SA_MealLog_GetByRange` and `SA_MealCost_GetMonthly` and must change together**, or the monthly statement and the 12-month trend put the same punch in two departments. `IsRuleMatched` gates the *read*, not just the write, so editing the rule retires stale periods with nobody cleaning the table. An expired period is not an undo: punches inside it keep the department they were given — last month's invoice must not move when this month's visitor arrives. The Ánh Xạ Bộ Phận popup drives this with an explicit **Áp dụng** form (guest, department, from, to — nothing is written until the button, and the client pre-checks the same overlap rule for a faster message), a table of periods with per-period delete, and a guest overview carrying punch counts and period counts.
- **The loss queue groups by working day, not calendar day, and splits losses into charged and free.** `evaluatePunchDays` keys on `getCostReportDate` — the same working-day rule the cost reports use — because CA1 runs 22:50→01:50: a punch at 00:05 and another at 23:45 on the same calendar date are two *different* night shifts, and grouping them by `actualDate` called ~40% of all duplicates falsely (438 of 1,114 in Aug 2026). Two rules then run per working day: one punch per shift, and at most 3 shifts. Each loss is further classed by `LossCharge` — a `TRUNG_CA` loss less than `FREE_DUP_WINDOW_MINUTES` (10) after the previous punch is `KHONG_TRU` (a re-swipe when the reader didn't take; nobody ate a second meal), everything else is `BI_TRU`. `EvaluatedPunch.gapMinutes` is measured from full datetimes via `Date.UTC`, never `new Date(string)` — the space-separated format parses as local time and drifts an hour across a DST boundary. Suất Ăn Mất Mát lists one row per (working day × user × class) so a mixed day can't produce an ambiguous "Phân loại" cell, and the Dashboard's loss card shows the `BI_TRU` figure so the two screens agree. Above that list sits a **working day × shift count table** with its own Bị trừ / Không trừ / Tất cả selector — deliberately separate state from the clickable summary cards that filter the list below, because one is a month-at-a-glance and the other is a per-case queue. Its shift columns come from `SA_Shift` so adding a shift needs no code change, and `'Khác'` only becomes a column when it actually has losses. It has its own **Excel export** ([lossStatsWorkbook.ts](src/components/lossStatsWorkbook.ts)) which writes exactly the scope on screen — the scope goes in the filename and in the sheet subtitle, so a downloaded file says which group it counts. The Navbar's red badge counts the *cases* (`abnormalList.length`), not the losses — on real data it fires in the hundreds per month, so it is a review queue, not an exception.
- **Prices come from `SA_MealPrice` by `code`**, always via `getUnitPrice(priceItems, code, fallback)` so a missing item degrades instead of producing `NaN`. The Vietnamese side has exactly two price points, matching the canteen's statement: `VN_CHINH` 28.000 for 23H/5H/12H/17H and `VN_PHU` 20.000 for 7H/19H. **The birthday price is not one of them.** `SUAT_DAC_BIET` survives in the table only as the fallback for a birthday date left without a price — the real unit price of a birthday meal is `SA_BirthdayConfig.SpecialMealPrice` of the day the meal was eaten, so it is *per date*, not per code, and it is edited in Cấu Hình Sinh Nhật. There is **no fixed labour/cleaning cost line in `SA_MealPrice`** — every *meal* figure the cost reports show is derived from punches, milk entries or manual entries. (`LABOR_COST` as a price item was removed on 2026-08-21; if you find that code referenced anywhere, it is stale. Hired-labour cost is a separate dated domain — see `SA_LaborCost` below — not a unit price.)
- **Which meal category a punch costs is configuration, not code.** `SA_ShiftMealCategory` maps `(ShiftCode, StaffType)` → one of the five categories `KO_COM / KO_MY / VN_CHINH / VN_PHU / VN_SINHNHAT`; users edit it in the Cấu Hình Giá Suất Ăn tab, and `ShiftCode` includes `'Khác'`. That tab offers **only the four non-birthday categories**, in the price table and in the per-shift dropdown alike: birthday pricing is a dated question and lives entirely in Cấu Hình Sinh Nhật, and a second place to type the number is a second place for it to go stale. A cell that still holds `VN_SINHNHAT` from before keeps showing it (the dropdown appends the current value when it is off-list) so nothing silently changes, but it cannot be picked again. `classifyMeal` takes that lookup and falls back to the original hard-coded rule (KR: CA3+CA4 cơm Hàn else mỳ Hàn; VN: CA1+CA4 bữa chính else bữa phụ) when a row is missing — `SA_MealCost_GetMonthly` implements the same fallback, so change both together. `StaffType` is `'KR'` **iff the large department is `KR`** — the reader is irrelevant, so KR staff get Korean prices at every machine and everyone else gets Vietnamese prices even at TA-102. That single rule lives in `isKoreanStaffLog` (client) and the `st` CROSS APPLY of `SA_MealCost_GetMonthly` (SQL).
- **The birthday override applies only to the birthday shifts.** `SA_SystemSetting.BIRTHDAY_SHIFTS` (default `CA1,CA4` — the two main meals) lists which shifts get `VN_SINHNHAT` on a date in `SA_BirthdayConfig`. Other shifts that day keep their normal price and Korean staff are never overridden. This is deliberately **not** derived from `SA_ShiftMealCategory`: pricing groups and birthday eligibility are different questions (CA2/CA5 are priced as `VN_CHINH` but do not get a birthday meal). The date compared is `mealDate`, not `actualDate` — birthday day 14 covers `14 22:50 → 15 01:50` for CA1, and `14 00:00–01:50` (CA1 of day 13) is *not* a birthday meal. Implemented in `isBirthdayMealLog` (client, which checks both conditions before `classifyMeal` sees a boolean) and in the `Category` CASE + `@BirthdayShifts` of `SA_MealCost_GetMonthly`.
- **Every birthday date carries its own price, so a birthday meal's unit price is a property of the day, not of a category.** `SA_BirthdayConfig.SpecialMealPrice` is the only source; `buildBirthdayPriceMap` turns the config rows into `date → price` and that one map serves as both the date lookup and the price lookup, so "this day is a birthday" and "this is the price" can never come from two places that disagree. `ClassifiedLog.unitPrice` and `CountedManualMeal.unitPrice` therefore carry the resolved price and **every cost table reads that field instead of `pricing[category]`** — `pricing.VN_SINHNHAT` is now only the fallback for a date left at 0. Consequences to keep in step: the monthly statement's **"Suất ăn đặc biệt SN" block is one row per distinct price** (`buildBirthdayBuckets`, dates of that price listed in NOTE), while the allocation table's Suất SN column and the department table's `VN_SINHNHAT` price cell hold the **unrounded weighted average** (`buildCategoryUnitPrices`) — average × total count is exactly the true total, which is what keeps `reconcileCost` balancing and the Excel `SUMPRODUCT` honest, so never round it. `SA_MealCost_GetMonthly` accumulates `SuatDacBietAmount` per punch rather than multiplying a count by one price; change one and you must change the other.
- **A manual entry is a real meal and counts everywhere a punch does.** The Nhập Thủ Công Ca tab exists for punches that never happened — reader down, power cut, someone eating unscheduled — but the canteen still cooked and still invoices, so every meal count and every cost figure in the app includes them. `classifyManualEntries` in [mealEngine.ts](src/services/mealEngine.ts) is the single pass that resolves one to the same shape as a punch (large department, staff group, meal category, unit price), mirroring `classifyLogs`; screens aggregate its output rather than re-deriving the rules. It feeds Dashboard (shift stats, KR/VN counts and amounts, the dept × shift matrix), Thống Kê Ca / Bộ Phận, Hàn Quốc vs Việt Nam, and every table in Báo Cáo Chi Phí including `buildDeptAllocation` and `buildShiftPivot`; `SA_MealCost_GetMonthly` does the same in SQL via a `UNION ALL` over `SA_ManualEntry` (one row carries `Quantity` meals, so the counting column is `Qty`, not a literal `1`). **What a manual entry cannot join is anything keyed on a person** — it has no `userId` and no punch time — so it stays out of the employee rows of `buildShiftPivot` (it gets its own `MANUAL_PIVOT_LABEL` footer row that keeps the sheet's totals right), out of Lịch Sử Chấm Ăn, and out of the abnormal-punch queue. Screens that show a punch list next to a count that includes manual meals say so in the subtitle. **Birthday pricing does apply to a Vietnamese manual entry** — someone who signed the book on the birthday day ate the birthday meal just as the person whose card read did — so a `'VN'` row whose date is in `SA_BirthdayConfig` and whose shift is a birthday shift becomes `VN_SINHNHAT` at that day's price, leaves the shift's Ký số row (`notBirthdayManual` filters it out of `manualSeries`) and joins the "Suất ăn đặc biệt SN" block instead. The date compared is the day the shift *starts* — the same key `getMealShiftDate` gives a punch — which for CA1 is the day **before** the date the operator typed (see the next bullets), and `mmd` in the SQL. Korean rows are never overridden. `classifyManualEntries` and the manual `UNION ALL` branch of `SA_MealCost_GetMonthly` both implement this; change one and you must change the other.
- **A manual entry carries its own `StaffType`, and the two groups land in the cost report differently.** `SA_ManualEntry.StaffType` is `'KR'` or `'VN'` — a manual entry is not tied to a person, so unlike a real punch it cannot derive the group from a department and the operator picks it. `'VN'` (the default, and what every row predating the column means) becomes a separate **"Ký số"** row under its shift in the 베트남 block, because the canteen reconciles those against signatures on paper. `'KR'` is **merged straight into the 한국 block's shift row** — same shift, same day column, priced at the Korean rate — with no Ký số row. `manualSeries` in [reportModel.ts](src/components/financial/reportModel.ts) takes the group as a required argument so neither block can silently pick up the other's entries, and `buildAllocationColumns` folds KR manual entries into Cơm Hàn / Mì Hàn by the category of `(shift, KR)` so the allocation table's total still matches the monthly statement's. `SA_MealCost_GetMonthly` groups manual entries by `MONTH(EntryDate)` and knows nothing about day columns, so the yearly trend is unaffected either way.
- **A manual entry's date is its working day, and its moment is the START of its shift within that day.** "CA1 ngày 26" is the night shift 25 22:50 → 26 01:50; CA2 ngày 26 is 26 04:30. `manualEntryDateTime` gives every row a `dateTime` of `date + SA_Shift.StartTime`, except the wrapping shift, which starts the evening *before* (`(date-1) 22:50`), and `reportDate` is simply `date` — no shift moves to another day column. **Every screen filters manual entries on `dateTime`, half-open** (`manualInRange`: `start <= dateTime < end`), inside `classifyManualEntries` itself, which therefore takes `startDateTime` / `endDateTime`. So filtering from 25 22:50 counts CA1 of the 26th onwards and nothing typed for the 25th, and a filter ending exactly at 25 22:50:00 does not pull in CA1 of the 26th. Every day-column key under `financial/` (`manualSeries`, `collectReportDates`, `buildShiftPivot`) reads `reportDate`. (Until 2026-09-29 the typed date was the day the shift *started* — CA1 of the 25th was invoiced under the 26th. Rows entered under that rule now read as one working day earlier.)
- **Supplies are issued in two shifts, and that is a separate catalogue from `SA_Shift`.** `SupplyShiftCode` is `'NGAY'` (Ca ngày) or `'DEM'` (Ca đêm) — not a `ShiftCode`, because the canteen hands things out twice a day regardless of the six punch windows. Rows predating the column default to `'NGAY'`, matched by `parseSupplyShift` ([mealEngine.ts](src/services/mealEngine.ts)) on the client. **One database row per (day, item, shift); one screen row per (day, item); one report row per shift.** Quản Lý Sữa shows a day as a single line with a *Ca ngày* and a *Ca đêm* quantity column and no shift column — `groupByDay` / `planDay` in [SupplyEntryManager.tsx](src/components/SupplyEntryManager.tsx) are the only place the two representations meet, and the Excel import takes the same day-shaped row. Saving a `(day, item, shift)` that already exists **overwrites** it rather than inserting a second row (a zero quantity deletes it), so re-importing the same file twice cannot double the day. "Thống kê suất ăn tháng" is where the split shows up again: the Sữa and Chi phí phát sinh blocks get **two sub-rows per item**, `Ca ngày` and `Ca đêm` in the DATE column, each carrying its own unit price and amount from `SupplySeries.byShift` — the day columns are one flat tier for every row, in the web table, the CSV and the Excel sheet alike. Every other report (allocation, per-shift, `SA_MealCost_GetMonthly`) totals per day.
- **In the cost-report tab a supply row has a time window, not just a date, and it is filtered on that window.** A row of day D covers **Ca đêm (D-1) 22:50 → D 08:00** and **Ca ngày D 08:00 → D 22:50** (`supplyShiftWindow` in [mealEngine.ts](src/services/mealEngine.ts); 22:50 is the wrapping shift's start, 08:00 is `SUPPLY_DAY_START`), and it counts when that half-open window overlaps the second-precision filter by more than a touch (`from < endDateTime && to > startDateTime`). So filtering from 25 23:00 drops both of the 25th's rows, and the 26th's night row is in — the same working-day boundary the punches' `reportDate` uses, and the day column is still the entry's own date. `FinancialReportView` filters **once** through `filterSupplyByRange` and hands the ranged arrays to every table, card and Excel sheet; `buildSupplySeries`, `collectReportDates`, `reconcileCost`, `buildMonthlyStatRows` and `buildAllocationColumns` trust their input and no longer take a date range. The Dashboard filters milk through the same `supplyInRange`; Quản Lý Sữa shows whole day rows and filters them by the working-day range `startDate`/`endDate`.
- **There are two supply domains and they are deliberately identical in shape: milk and `SA_ExtraCost`.** Extra costs are anything the canteen invoices beyond meals and milk — ice cream, a one-off holiday handout — with a free-text `CostType` the user names. `SA_ExtraCost` mirrors `SA_MilkEntry` column for column, its three procs mirror the milk procs, and both feed `buildSupplySeries` in [reportModel.ts](src/components/financial/reportModel.ts) through the `milkAsSupply` / `extraAsSupply` adapters — so keep the two tables the same shape, and when you change how one reaches a report, change the other. In the UI they are two sections of the **Quản Lý Sữa** tab, both rendered by the one [SupplyEntryManager](src/components/SupplyEntryManager.tsx) (labels, colours and Excel-template samples come from a config object; there is no second copy of that form). On the monthly statement the **Sữa** block comes first and **Chi phí phát sinh** directly below it. Neither is attributable to a department, so both stay out of `buildDeptAllocation` and appear instead as reconciliation lines via `reconcileCost`.
- **Hired-labour cost is the one cost domain with a publish step, and that is its whole point.** The canteen hires workers by *stint*: one person, one date range, one sum for the whole range. `SA_LaborCost` is a **draft** nobody's report reads; pressing **Áp dụng** copies it into `SA_LaborCostApplied` under a new `SA_LaborCostBatch` row, and only the **newest batch** feeds money into the reports — summing every batch would double the cost the second time anyone presses the button, and older batches stay untouched as the audit trail. So "editing rows changes nothing until you apply" is a property of one line in `FinancialReportView` (it reads `laborCosts.appliedRows`, never `laborCosts.draft`), not a convention anyone has to remember. The batch also **freezes its `WorkDayRule`** (`ALL` / `MON_SAT` / `MON_FRI`), so changing the rule for the next stint cannot make last month's settled figure move on its own.
- **A labour stint's date range is half-open — `EffectiveFrom` counts, `EffectiveTo` does not — and every other date in this codebase is inclusive.** This is the only way the handover day works: users write consecutive stints the way they write them on paper (25/07→25/08 then 25/08→25/09), and the 25th of August must belong to exactly one of them, neither billed twice nor dropped. `CK_SA_Labor_Range` therefore demands `EffectiveTo > EffectiveFrom` (equal is an empty stint), both bounds are required (the divisor needs a length), and the UI labels the two fields "Có tính ngày này" / "KHÔNG tính ngày này" and prints the last day actually counted rather than the raw end date. Two stints of the **same person** may not overlap (`aFrom < bTo AND bFrom < aTo`) — `SA_LaborCost_Save` blocks it per row and `SA_LaborCost_Apply` re-checks the whole set before freezing; different people sharing a range is normal and each is computed independently.
- **`buildLaborSegments` is the only implementation of the proration, and it is deliberately not in SQL.** Money for a filter range is `stint amount ÷ working days of the whole stint × working days of the overlap`, and every case in the spec — filter inside a stint, filter covering it, filter clipping one end, filter spanning several consecutive stints — is that one intersection `[max(start), min(end))`, with no special branch. A segment that covers its stint exactly returns the **entered amount verbatim** rather than dividing and multiplying back, so nobody sees 7.999.999 where they typed 8.000.000. `dailyRate` is never rounded (an Excel formula multiplies it — same rule as milk's average unit price); rounding happens only where it is displayed. The 12-month table gets labour from `withLaborCost`, which calls that same function once per month on the client — `SA_MealCost_GetMonthly` knows nothing about labour and should stay that way, because a T-SQL copy of the working-day arithmetic is exactly the second implementation this file keeps warning about. `MonthlyCostRow.ChiPhiNhanCong` is therefore absent on rows straight from the API; read it through `yearlyValue`. **The filter reaches labour as working days, not calendar dates**: `costWorkDayRange` ([mealEngine.ts](src/services/mealEngine.ts)) turns the second-precision filter into the inclusive range of working days it touches — working day D is (D-1) 22:50 → D 22:50, the same boundary as `reportDate` and the supply windows — so 25 22:50 → 29 22:50 bills days 26–29 only. `FinancialReportView` passes that range, never `startDate`/`endDate`, to `buildLaborSegments`.
- **Labour cost is not attributable to a department, so it lives in `reconcileCost` beside milk and extra costs**, never in `buildDeptAllocation`: the workers serve the whole canteen. It appears as its own summary card, a block directly under "Chi phí phát sinh" in the monthly statement (one row per person × stint, day cells marking each *working day* so `TOTAL × ĐƠN GIÁ` still holds), a reconciliation row at the foot of the department table, a column in the allocation table, and a series in the 12-month table and trend chart. It stays out of the six per-shift pivots, which count meals and have no money column at all.
- **`SA_Shift.ShiftReName`** is the canteen-facing name of a shift, editable per site; display only (Dashboard). The cost reports do *not* read it — they use the fixed `REPORT_SHIFT_LABEL` map in `mealEngine.ts` (`23H`/`5H`/`7H`/`12H`/`17H`/`19H`), so every sheet names a shift the same way and the sheets stay cross-referenceable. CA1 is `23H` everywhere. Where the two differ, `ShiftDailyPivotReport` shows both.

## Authentication

Every `/api/*` endpoint requires a session. [server/auth.js](server/auth.js) registers `/auth/login`, `/auth/logout` and `/auth/me` and then installs `requireAuth` as router middleware, so **any endpoint added below that line is protected by default** — the open list is a whitelist, not a blacklist, and forgetting to declare a new route leaves no hole. `npm run lint` won't catch an auth mistake; the shape of the router is what protects you.

Four things here are deliberate and should not be traded away:

- **Passwords are stored in plain text, deliberately.** The owner chose this because the server only runs on the plant LAN; the cost is that anyone who can read `SA_User` reads everyone's password. `preparePassword` in [auth.js](server/auth.js) is the single place that decides the stored form — return a `scrypt$…` string from it to turn hashing back on, and `verifyPassword` already reads both forms so no account gets locked out either way. Comparison still uses `crypto.timingSafeEqual`, not `===`.
- **The session token lives in an `httpOnly` cookie**, never in `localStorage` — page JavaScript cannot read it, so one XSS bug does not hand over everyone's session. The client sets `credentials: 'same-origin'` in [api.ts](src/services/api.ts); drop that and every call 401s.
- **The database stores only the SHA-256 of the token** (`SA_Session.TokenHash`), so reading `SA_Session` does not let anyone impersonate a session. Logout deletes the server row, not just the cookie.
- **Data loading is gated on `user`.** The effects in [App.tsx](src/App.tsx) that fetch meal logs and the yearly trend list `user` in their dependencies. Without it they fire once on page load — before login — get a 401, and never re-run because the date range hasn't changed, so the user logs in to an empty screen. Anything new that fetches on mount must be gated the same way.
- **A failed login never says whether the username exists** — same message, and a hash is computed even for unknown users so the response time doesn't leak it either.

"Ghi nhớ đăng nhập" sets the cookie and the `SA_Session` row to `AUTH_SESSION_DAYS` (7); unticked it is `AUTH_SHORT_SESSION_HOURS` (12). `REMEMBER_DAYS` in [App.tsx](src/App.tsx) is display-only and must be kept in step. Remembering the *password* on the client is left to the browser's own password manager — the login form carries the standard `autocomplete` attributes for it.

`AUTH_SECURE_COOKIE` is `false` because the site runs plain HTTP on the plant LAN; set it to `true` the day it moves to HTTPS, or the cookie stops being sent and nobody can log in.

Accounts are managed from the server, not from a screen inside the app: `npm run user -- list | add <name> "<Display>" [password] | passwd <name> [password] | disable <name> | enable <name>`. Omit the password and one is generated; `list` shows it, since it is stored in the clear and that is the point of the choice — no endpoint ever returns it, only the CLI. Changing a password or disabling an account also kills that account's open sessions (`SA_User_Save`).

## Conventions

- **Dates and times are compared as strings throughout** — `"YYYY-MM-DD"` and `"HH:mm:ss"` sort and compare lexicographically. Procedures return pre-formatted `char(10)` / `char(8)` / `char(19)` so this holds end to end. Don't introduce `Date` objects into comparison paths.
- **Date params cross the wire as `YYYY-MM-DD` strings**, bound as `sql.VarChar(10)`, never as JS `Date` — SQL Server parses ISO strings into `date` unambiguously, and binding `Date` reintroduces timezone drift.
- Never build SQL by string concatenation in the server; add a procedure instead. All params go through the `parse*` validators in `server/routes.js`.
- `RAISERROR` messages in procedures are user-facing Vietnamese — they propagate through the API error handler into the UI `alert`.
- Tailwind v4 via `@tailwindcss/vite`; [src/index.css](src/index.css) is just `@import "tailwindcss"`. No config file, no custom theme — the dark slate/amber look is inline utility classes.
- Icons from `lucide-react`, charts from `recharts`, currency via `formatVND` (`Intl.NumberFormat('vi-VN')`).
- CSV export goes through `exportToCSV(filename, headers, rows)`, which prepends a UTF-8 BOM so Excel renders Vietnamese diacritics correctly.
- The `@/*` → project-root alias is configured in both [tsconfig.json](tsconfig.json) and [vite.config.ts](vite.config.ts), but no source file uses it; imports are relative.
- TypeScript runs with `noEmit` and **without** `strict` — `strictNullChecks` is off. The `server/` directory is plain JavaScript and is not type-checked.
- `.env` holds the DB password and is gitignored. Quote it — dotenv treats an unquoted `#` as a comment, which silently truncates the password.
